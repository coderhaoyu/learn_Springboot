# 产品设计：我们的冒险

> 本文先确定完整的前后端产品边界，再按照“先后端、后前端”的方式执行。
>
> 当前目标不是一次写完所有功能，而是先把模块之间的关系、接口职责和版本边界想清楚，避免开发过程中不断改方向。

## 1. 产品定位

“我们的冒险”是一个面向两个人的私密共同成长应用。用户绑定伴侣后，可以参加共同挑战、记录每日打卡、查看进度和成就，也可以保存重要的生活片段和纪念日。

第一版不做聊天软件，也不做公开社交平台。核心闭环只有一条：

```text
注册登录
    ↓
绑定伴侣
    ↓
选择共同挑战
    ↓
完成每日打卡
    ↓
累计进度和积分
    ↓
查看共同记录和成就
```

## 2. 产品目标和非目标

### 2.1 目标

- 让两个人有一个私密、连续的共同记录空间。
- 通过挑战、进度和成就增加使用趣味。
- 用一个可控的业务场景学习完整后端开发流程。
- 后端接口稳定后，再开发一个有时间线和进度感的前端应用。

### 2.2 非目标

第一版明确不做：

- 实时聊天、语音和视频；
- 消息推送和短信通知；
- 图片、视频和大文件存储；
- 地图轨迹和第三方登录；
- 礼物商城、支付和虚拟货币；
- 多人群组和复杂社交关系；
- AI 生成情书或自动推荐；
- 微服务、消息队列和分布式部署。

这些内容可以作为后续练习，但不进入当前后端学习主线。

## 3. 版本规划

### V1：后端核心闭环

必须完成：

1. 用户注册、登录和当前用户；
2. 邀请码绑定情侣关系；
3. 系统预置共同挑战；
4. 情侣加入和退出挑战；
5. 每日共同打卡；
6. 挑战进度和积分查询；
7. 私密数据访问权限；
8. 关键重复操作的数据库约束和事务处理。

V1 的打卡规则刻意简化为：**一个情侣在一个挑战中每天只有一条共同打卡记录，由任意一方提交，记录作者用于展示**。这样可以先理解唯一约束、事务和幂等性，不急着处理双方分别打卡的复杂进度合并。

### V1.5：后端扩展模块

在 V1 稳定后增加：

- 共同生活记录（时光记录）；
- 纪念日和倒计时；
- 固定规则的成就解锁；
- 首页汇总数据；
- 按日期、心情和挑战筛选。

### V2：前端实现

后端核心和扩展模块完成、接口文档稳定后，再开发前端：

- 登录和注册；
- 情侣绑定引导；
- 首页共同进度；
- 挑战列表和详情；
- 每日打卡日历；
- 时光记录时间线；
- 纪念日倒计时；
- 成就展示；
- 个人资料和设置。

前端是后续阶段，不进入当前八周后端学习任务的交付标准。

## 4. 后端模块设计

后端采用单体 Spring Boot 应用，按业务模块组织代码。每个模块内部再划分 Controller、Service、Mapper、Entity、DTO 和 VO，避免把所有类继续堆在同一个目录中。

| 模块 | 主要职责 | V1 范围 |
|---|---|---|
| `common` | 统一响应、分页、异常、配置 | 必须 |
| `auth` | 注册、登录、Token 签发 | 必须 |
| `user` | 当前用户资料和认证查询 | 必须 |
| `couple` | 邀请码、绑定关系、伴侣信息 | 必须 |
| `challenge` | 挑战目录、挑战详情、参与关系 | 必须 |
| `checkin` | 每日打卡、进度、积分 | 必须 |
| `moment` | 共同生活记录和时间线 | V1.5 |
| `anniversary` | 纪念日和即将到来查询 | V1.5 |
| `achievement` | 成就规则和解锁记录 | V1.5 / 结业练习 |
| `dashboard` | 首页汇总和统计 | V1.5 |

### 4.1 `common`

负责：

- `ApiResponse<T>`；
- `PageResult<T>`；
- 业务异常；
- 全局异常处理；
- 安全相关公共配置；
- 后续的统一日志和时间配置。

### 4.2 `auth` 和 `user`

`auth` 负责认证入口和 Token，`user` 负责用户资料与认证查询。两者相关但职责不同：

- `auth`：我是谁，如何登录；
- `user`：我的资料是什么；
- 业务模块：我能访问什么。

### 4.3 `couple`

负责：

- 创建绑定邀请；
- 使用邀请码完成绑定；
- 查询当前情侣关系；
- 查询伴侣公开资料；
- 判断用户是否属于某个情侣关系。

### 4.4 `challenge`

V1 只使用系统预置挑战，避免一开始加入复杂的挑战编辑器。模块负责：

- 查询可参加的挑战；
- 查看挑战详情；
- 加入挑战；
- 查询当前情侣参加的挑战；
- 退出尚未开始的挑战。

用户自定义挑战放到后续版本。

### 4.5 `checkin`

负责：

- 创建当天共同打卡；
- 查询挑战打卡时间线；
- 查询完成天数、连续天数和积分；
- 防止重复打卡；
- 在挑战完成时触发后续成就判断。

### 4.6 `moment`、`anniversary`、`dashboard`

这些模块用于丰富产品体验，但不应阻塞前面的核心学习：

- `moment`：文本形式的共同生活记录；
- `anniversary`：重要日期和周期类型；
- `dashboard`：把多个模块的数据汇总为首页展示结果。

## 5. 前端模块设计

前端先在仓库根目录的 `frontend/` 中创建 React 工程骨架；业务页面和接口联调在后端接口稳定后实现。

前端技术栈使用 React、TypeScript、Vite、React Router、Zustand 和 Axios。

### 5.1 页面模块

| 页面模块 | 页面职责 | 依赖的后端模块 |
|---|---|---|
| 认证 | 注册、登录、退出 | `auth`、`user` |
| 情侣引导 | 生成邀请码、输入邀请码、查看绑定状态 | `couple` |
| 首页 | 展示在一起天数、当前挑战、进度和纪念日 | `couple`、`checkin`、`anniversary`、`dashboard` |
| 挑战 | 浏览挑战、查看详情、加入挑战 | `challenge` |
| 打卡 | 今日打卡、打卡日历、进度和连续天数 | `checkin` |
| 时光记录 | 时间线、新增、编辑、删除记录 | `moment` |
| 纪念日 | 列表、倒计时、新增和编辑 | `anniversary` |
| 成就 | 查看已解锁和待解锁成就 | `achievement` |
| 个人设置 | 昵称、头像地址、退出登录 | `user`、`auth` |

### 5.2 前端基础层

后续前端实现时再建立：

- `api/`：按后端模块封装请求；
- `stores/`：认证用户、情侣关系和当前挑战状态；
- `router/`：登录守卫和页面路由；
- `components/`：时间线卡片、进度环、纪念日卡片等复用组件；
- `views/`：按页面模块组织视图；
- `types/`：与后端 VO 对应的前端类型。

前端不直接猜测业务规则。能否打卡、是否有权限、积分是多少，都以服务端结果为准。

## 6. 核心数据模型

以下是设计层面的字段和关系，不要求现在一次性写入数据库。实现每张表前，先由学习者自己确定字段类型、约束和索引，再进行代码评审。

### 6.1 V1 必要表

#### `users`

保存用户基础信息和认证所需信息：

- 主键；
- 昵称；
- 邮箱；
- 密码摘要；
- 头像地址（可暂时为空）；
- 创建时间和更新时间。

当前项目已有用户表和用户 CRUD，可以作为第一阶段基础。

#### `couples`

保存已经建立的情侣关系：

- 主键；
- 两个用户的关联；
- 关系状态；
- 绑定时间；
- 结束时间（后续关系结束功能使用）。

V1 只允许一条有效关系对应两个用户。

#### `couple_invitations`

保存绑定邀请的生命周期：

- 邀请人；
- 邀请码或邀请码摘要；
- 过期时间；
- 邀请状态；
- 使用时间。

邀请码必须具备唯一性、有效期和一次性使用规则。

#### `challenges`

保存系统挑战：

- 标题；
- 描述；
- 目标天数；
- 开始日期和结束日期；
- 挑战状态；
- 创建来源（系统或用户，用户创建放后续）；
- 创建时间。

#### `couple_challenges`

保存情侣参加挑战的关系：

- 情侣关系；
- 挑战；
- 参与状态；
- 加入时间；
- 完成时间；
- 累计积分；
- 版本号（后续并发更新练习使用）。

同一情侣不能重复加入同一个挑战。

#### `check_ins`

保存每日共同打卡：

- 参与挑战关系；
- 提交人；
- 打卡日期；
- 备注；
- 心情；
- 创建时间。

V1 的唯一业务标识是“一个参与挑战在某一天的共同打卡”，需要在数据库和 Service 两层共同保护。

### 6.2 V1.5 扩展表

#### `moments`

保存普通生活记录：

- 情侣关系；
- 创建人；
- 标题；
- 文本内容；
- 发生日期；
- 心情；
- 可见性；
- 创建时间和更新时间。

#### `anniversaries`

保存纪念日：

- 情侣关系；
- 标题；
- 纪念日期；
- 是否按年重复；
- 备注；
- 创建时间和更新时间。

#### `achievements` 与 `couple_achievements`

前者保存系统成就定义，后者保存情侣解锁结果。成就规则先固定在代码或配置中，后续再学习可配置规则。

### 6.3 关系图

```text
users
  ├── couples（用户 A / 用户 B）
  └── couple_invitations（邀请人）

couples
  ├── couple_challenges ── challenges
  │         └── check_ins
  ├── moments
  ├── anniversaries
  └── couple_achievements ── achievements
```

## 7. 后端 API 目录

以下只确定资源和职责，不直接替代实现阶段的接口设计练习。

### 7.1 认证和用户

- `POST /api/auth/register`：注册；
- `POST /api/auth/login`：登录并返回 Token；
- `GET /api/users/me`：获取当前用户；
- `PATCH /api/users/me`：修改当前用户资料。

### 7.2 情侣关系

- `POST /api/couples/invitations`：创建绑定邀请；
- `POST /api/couples/bind`：使用邀请码绑定；
- `GET /api/couples/me`：查询当前情侣关系；
- `POST /api/couples/end`：结束关系，后续版本开放。

### 7.3 挑战和参与

- `GET /api/challenges`：查询可参加挑战；
- `GET /api/challenges/{id}`：查询挑战详情；
- `POST /api/challenges/{id}/join`：当前情侣加入挑战；
- `GET /api/couples/me/challenges`：查询当前情侣参加的挑战；
- `GET /api/couples/me/challenges/{id}`：查询参与详情和进度；
- `POST /api/couples/me/challenges/{id}/leave`：退出尚未开始的挑战。

### 7.4 打卡和进度

- `POST /api/couples/me/challenges/{id}/check-ins`：提交当天共同打卡；
- `GET /api/couples/me/challenges/{id}/check-ins`：分页查询打卡记录；
- `GET /api/couples/me/challenges/{id}/progress`：查询进度、连续天数和积分。

### 7.5 时光记录和纪念日

- `POST /api/moments`、`GET /api/moments`、`GET /api/moments/{id}`；
- `PUT /api/moments/{id}`、`DELETE /api/moments/{id}`；
- `POST /api/anniversaries`、`GET /api/anniversaries`；
- `PUT /api/anniversaries/{id}`、`DELETE /api/anniversaries/{id}`；
- `GET /api/dashboard/summary`：查询首页汇总数据。

## 8. 权限和并发规则

### 8.1 权限规则

- 注册和登录不要求登录；
- 绑定后的业务数据只对情侣双方开放；
- 当前用户身份从安全上下文获得，不能相信请求体中的用户 id；
- 记录作者可以修改和删除自己的记录；
- 共享挑战和共同打卡由情侣双方共同访问；
- 任何资源访问前，Service 都要验证当前用户是否属于对应情侣关系。

### 8.2 并发练习规则

V1 只练习单体应用中的数据一致性，不引入分布式锁：

1. 同一天重复打卡：数据库唯一约束兜底；
2. 邀请码同时使用：状态从“未使用”到“已使用”必须是条件更新；
3. 积分更新：先理解丢失更新，再选择重新统计、原子更新或乐观锁；
4. 成就解锁：同一成就只能为同一情侣创建一次解锁记录。

事务负责保证一组操作一起成功或回滚，唯一约束、条件更新和版本号负责解决具体的并发竞争，两者不能混为一谈。

## 10. 完成定义

后端核心完成的标准：

- 两个用户可以注册、登录并完成情侣绑定；
- 情侣可以加入挑战并查看参与详情；
- 每天可以提交一次共同打卡；
- 重复打卡、越权访问和无效邀请码会被正确拒绝；
- 进度和积分查询结果与打卡记录一致；
- 关键业务有 Mapper、Service 和接口层面的定向测试；
- 可以解释每个请求从 HTTP 到 MySQL 再回到 JSON 的完整路径。

前端阶段完成的标准：

- 用户可以不依赖接口工具完成上述完整流程；
- 前端路由、状态和 API 层职责清晰；
- 页面显示以服务端返回为准；
- 错误状态和登录失效有明确的用户提示；
- 前后端接口文档与实际行为一致。
