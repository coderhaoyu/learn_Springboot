# 第 4 周：情侣绑定与关系权限

> 建议投入：17–20 小时
> 对应总计划：[PLAN.md](../../PLAN.md)
> 完整产品设计：[couple-challenge-design.md](../couple-challenge-design.md)

## 当前目标

把两个独立用户绑定为一段情侣关系，第一次练习邀请状态、跨表操作、事务和资源级权限。

```text
用户 A 创建邀请
    ↓
用户 B 使用邀请码
    ↓
验证有效期和使用状态
    ↓
创建情侣关系并更新邀请状态
```

## 本周完成标准

- [ ] 能解释 `couples` 和 `couple_invitations` 的职责；
- [ ] 邀请码有唯一性、有效期和一次性使用规则；
- [ ] 用户不能绑定自己；
- [ ] 已绑定用户不能重复建立有效关系；
- [ ] 绑定成功后双方都能查询伴侣信息；
- [ ] 非情侣成员不能访问情侣资源；
- [ ] 绑定相关多步写操作具备事务边界；
- [ ] Controller 不自行判断情侣关系。

## 设计前必须确定

先写设计稿，不直接写代码：

1. 一名用户是否允许同时存在多段有效关系？第一版选择“不允许”；
2. 邀请码有效期多长？
3. 邀请状态有哪些？
4. 绑定成功时需要写入和更新哪些记录？
5. 结束关系是否进入当前版本？建议先只设计，不实现。

## 编写步骤

### 第 1 步：设计关系表

明确：

- 两个用户如何关联；
- 如何表示关系状态；
- 如何保证有效关系不会重复；
- 查询某个用户当前关系需要什么条件。

### 第 2 步：完成创建邀请

Service 需要负责：

- 获取当前用户；
- 检查当前用户是否可以发起邀请；
- 生成邀请信息；
- 保存过期时间和状态；
- 不把不必要的敏感字段返回给客户端。

### 第 3 步：完成绑定

按顺序实现和验证：

1. 读取当前用户；
2. 查询邀请码；
3. 判断邀请码状态和有效期；
4. 判断邀请人和接受人不是同一人；
5. 判断双方当前关系状态；
6. 创建情侣关系；
7. 更新邀请为已使用。

### 第 4 步：补充关系权限

所有需要情侣关系的业务接口，都应该复用一个清晰的 Service 判断思路，而不是信任客户端传来的 `coupleId`。

## 验收矩阵

| 场景 | 预期结果 |
|---|---|
| 创建有效邀请 | 成功返回邀请信息 |
| 输入有效邀请码 | 绑定成功 |
| 邀请码不存在 | 404 或明确业务错误 |
| 邀请码过期 | 409 |
| 邀请码重复使用 | 409 |
| 自己绑定自己 | 409 |
| 已有有效关系再次绑定 | 409 |
| 非情侣用户访问关系数据 | 403 |

## 事务练习

绑定过程至少包含两项持久化变化：

```text
创建情侣关系
    ↓
更新邀请状态
```

人为让第二项失败，观察第一项是否回滚。然后回答：

- 事务应该放在哪一层？
- 为什么不能在 Controller 里手动拼事务流程？
- 事务保证了什么，没有保证什么？
