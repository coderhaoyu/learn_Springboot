# 第 5 周：任务模块与复杂查询

> 建议投入：18–20 小时  
> 对应总计划：[PLAN.md](../../PLAN.md)

## 当前目标

完成任务 CRUD、组合筛选和状态流转，并通过 `version` 字段练习一次乐观锁。重点理解动态 SQL 如何由查询条件生成，以及数据库如何防止并发更新互相覆盖。

## 本周完成标准

- [ ] `tasks` 表包含项目、负责人、标题、描述、状态、优先级、截止时间和版本号。
- [ ] 任务具备新增、详情、分页、修改、删除接口。
- [ ] 分页支持按状态、负责人、优先级组合筛选。
- [ ] 动态 SQL 只拼接实际提供的条件。
- [ ] 状态变化遵循明确的流转规则。
- [ ] 修改和状态更新使用版本号实现乐观锁。
- [ ] 两个请求使用同一版本修改时，只允许一个成功，另一个返回 409。
- [ ] 能结合实际查询说明联合索引的字段顺序。

## 设计前必须确定

### 任务状态

先使用简单状态，例如：

```text
TODO → IN_PROGRESS → DONE
```

需要明确是否允许回退、是否允许跳过中间状态，以及谁可以操作。不要在规则不明确时开始写 SQL。

### 权限规则

- 项目成员可以查看项目中的任务。
- 项目成员可以新增和管理任务。
- 任务负责人必须是当前项目成员。
- 项目负责人延续第 4 周的项目管理权限。

### 并发更新

客户端修改任务时携带它读取到的 `version`。更新 SQL 同时匹配 `id` 和旧版本，并在成功时将版本加一；受影响行数为 0 表示数据已被其他请求修改。

## 需要创建或调整的职责

- 任务 Entity：对应 `tasks` 表。
- 新增、修改、筛选和状态更新 DTO：分别表达不同请求语义。
- 任务 VO：控制响应字段。
- Task Controller：接收路径、筛选条件和请求体。
- Task Service：成员校验、负责人校验、状态规则与乐观锁冲突判断。
- Task Mapper/XML：CRUD、动态条件、分页、计数和带版本条件的更新。
- 数据库脚本：任务表、外键和索引。

## 每日安排

### 周一：需求、表与接口设计（3 小时）

1. 写出任务字段及每个字段的类型、约束和来源。
2. 设计任务与项目、负责人之间的关系。
3. 写出任务 CRUD、列表筛选、状态更新接口表。
4. 画出任务状态机和允许的转换方向。
5. 写出负责人必须属于项目的业务校验流程。
6. 准备至少两个项目、三个用户的测试数据方案。

当天产出：表结构草图、接口表、状态流转图、权限规则。

### 周二：新增与详情（3 小时）

1. 创建任务相关 Entity、DTO 和 VO。
2. 新增前依次验证项目存在、当前用户是项目成员、负责人也是项目成员。
3. Mapper 写入任务，并处理自增主键和初始版本号。
4. 详情查询先完成资源级权限校验。
5. 分别测试合法负责人、非项目成员负责人和不存在项目。

检查题：为什么“负责人属于项目”是 Service 业务规则，而不是 Controller 参数格式校验？

### 周三：分页与动态 SQL（3 小时）

1. 先实现只按项目分页，再逐项增加状态、负责人和优先级条件。
2. 数据 SQL 和总数 SQL 使用完全一致的筛选条件。
3. 每增加一个条件，就验证单条件和与已有条件组合的结果。
4. 开启或查看 SQL 日志，确认没有传入的条件不会出现在 WHERE 中。
5. 保证分页排序稳定，例如同时使用业务排序字段和主键。

当天产出：筛选条件组合表，以及每组条件对应的预期任务 id。

### 周四：修改、删除与状态流转（3 小时）

1. 修改前校验任务存在、项目成员权限及新负责人合法性。
2. 删除前校验任务所属项目权限。
3. 状态更新使用独立入口和 DTO，不与普通字段修改混在一起。
4. Service 根据旧状态和目标状态判断是否允许流转。
5. 验证合法流转、非法跳转和重复设置相同状态。

检查题：状态流转为什么不应该只由一条无条件 UPDATE 完成？

### 周五：乐观锁（3 小时）

1. 详情响应包含当前 `version`。
2. 修改和状态更新请求携带旧版本。
3. 更新条件同时包含任务 id 与旧版本。
4. 更新成功时把版本加一。
5. Service 根据受影响行数把并发冲突映射为 409。
6. 不使用“更新前再查一次版本”替代 SQL 条件，因为两步之间仍可能发生并发修改。

当天产出：一张两个请求同时更新同一版本的时间线。

### 周六：组合筛选、并发与索引验证（4–5 小时）

1. 为不同状态、负责人和优先级准备足量任务数据。
2. 验证无筛选、单筛选、双筛选、三筛选及空结果。
3. 两个请求先读取相同版本，再依次提交不同修改。
4. 确认第一个成功、版本加一，第二个返回 409 且没有覆盖数据。
5. 根据实际高频查询设计一个联合索引，并记录为什么采用该字段顺序。

### 周日：定向测试与复盘（2 小时）

1. 为组合筛选、非法负责人、非法状态流转和乐观锁冲突补充相关测试。
2. 只运行任务模块涉及的测试。
3. 不看代码，口述一次三条件分页查询如何形成最终 SQL。
4. 手写乐观锁 UPDATE 的条件结构，并解释受影响行数为 0 的两种可能。

## 筛选验收矩阵

| 状态 | 负责人 | 优先级 | 预期检查 |
|---|---|---|---|
| 无 | 无 | 无 | 返回项目全部任务 |
| 有 | 无 | 无 | 只按状态过滤 |
| 无 | 有 | 有 | 同时满足负责人和优先级 |
| 有 | 有 | 有 | 同时满足全部条件 |
| 不匹配 | 任意 | 任意 | 返回空列表且总数为 0 |

## 乐观锁验收步骤

1. 请求 A、B 都读取任务，得到 `version = 3`。
2. A 携带版本 3 更新成功，数据库版本变为 4。
3. B 仍携带版本 3 更新。
4. B 的更新影响 0 行，接口返回 409。
5. 最终数据保留 A 的修改，没有被 B 覆盖。

## 学习重点

- MyBatis 动态 SQL 负责按输入条件组织 SQL，Service 负责业务规则。
- 分页数据查询与总数查询的 WHERE 条件必须一致。
- 状态机让“允许发生的变化”成为明确业务规则。
- 乐观锁不锁住整段读取时间，而是在写入瞬间检测版本是否过期。
- 索引应服务于真实查询，不能脱离 WHERE、排序与数据分布机械添加。
