# 第 6 周：打卡、进度与并发一致性

> 建议投入：18–20 小时
> 对应总计划：[PLAN.md](../../PLAN.md)
> 完整产品设计：[couple-challenge-design.md](../couple-challenge-design.md)

## 当前目标

实现“我们的冒险”最有特色的模块：每日共同打卡、连续天数、积分和并发一致性。

V1 的业务约定是：**一个情侣在一个挑战中每天只有一条共同打卡记录，由任意一方提交**。

## 本周完成标准

- [ ] 情侣只能为自己参加的挑战打卡；
- [ ] 只能在挑战有效日期内打卡；
- [ ] 同一天不能重复打卡；
- [ ] 能查询打卡时间线；
- [ ] 能计算完成天数和连续天数；
- [ ] 能查询当前积分；
- [ ] 重复请求不会重复增加积分；
- [ ] 能解释事务、唯一约束、原子更新和乐观锁的区别；
- [ ] 至少有一个定向并发场景验证数据一致性。

## 关键并发场景

### 场景一：双方同时提交当天打卡

必须防止两条相同日期的打卡记录同时写入。

思考顺序：

1. Service 先查是否存在有什么作用？
2. 为什么先查后写仍然有竞态？
3. 数据库唯一约束如何兜底？
4. 重复键异常如何转换成业务响应？

### 场景二：积分更新丢失

如果把积分总数单独保存，需要考虑两个请求同时读取旧积分并互相覆盖。

第一版可以选择从打卡记录重新统计积分，先保证结果正确；理解问题后，再尝试原子更新或版本号。

### 场景三：成就重复解锁

后续成就模块需要保证同一情侣的同一成就只能解锁一次。唯一约束和幂等写入是主要练习方向。

## 编写步骤

### 第 1 步：设计打卡表

确认：

- 打卡记录关联 `couple_challenges` 还是直接关联情侣和挑战；
- 打卡日期使用什么 Java 和 SQL 类型；
- 一天一条记录的唯一业务键是什么；
- 提交人字段用于什么展示；
- 打卡备注和心情是否允许为空。

### 第 2 步：实现正常打卡

```text
取得当前用户和当前情侣
    ↓
确认参与关系存在且状态允许打卡
    ↓
确认日期处于挑战范围
    ↓
写入当天打卡
    ↓
返回最新进度
```

### 第 3 步：实现进度查询

先用可解释的查询完成：

- 总打卡天数；
- 当前连续天数；
- 完成比例；
- 当前积分。

不要为了性能过早引入缓存。

### 第 4 步：验证并发一致性

使用定向测试或受控的并发请求，验证：

- 多次提交同一日期只产生一条记录；
- 重复请求不会重复奖励；
- 失败请求不会留下半成品数据。

## 验收矩阵

| 场景 | 预期结果 |
|---|---|
| 正常打卡 | 创建一条记录并返回进度 |
| 同日重复打卡 | 409 或明确重复业务错误 |
| 挑战未开始 | 拒绝打卡 |
| 挑战已结束 | 拒绝打卡 |
| 未参加挑战 | 403 或业务错误 |
| 查询打卡时间线 | 分页和排序稳定 |
| 并发重复提交 | 数据库只有一条有效记录 |
| 打卡失败 | 不产生错误积分或残留状态 |

## 周末复盘问题

1. 事务为什么不能单独解决所有并发问题？
2. 唯一约束和 Service 查重各自处于什么位置？
3. 什么是丢失更新？
4. 什么时候可以从明细记录重新统计，而不是保存汇总字段？
5. 如果以后要支持双方分别打卡，唯一业务键需要怎样变化？
6. 为什么当前阶段不直接引入 Redis 分布式锁？
