# 第 7 周：时光记录、纪念日与汇总

> 建议投入：17–20 小时
> 对应总计划：[PLAN.md](../../PLAN.md)
> 完整产品设计：[couple-challenge-design.md](../couple-challenge-design.md)

## 当前目标

在挑战和打卡核心闭环稳定后，增加有产品温度的记录模块，并练习时间查询、多表查询和聚合结果。

本周仍然只开发后端，不创建前端页面。

## 本周完成标准

- [ ] 完成文本形式的时光记录 CRUD；
- [ ] 记录列表只返回当前情侣可访问的数据；
- [ ] 记录作者可以修改和删除自己的记录；
- [ ] 支持按日期分页查询时间线；
- [ ] 完成纪念日 CRUD；
- [ ] 能查询即将到来的纪念日；
- [ ] 能返回首页所需的汇总数据；
- [ ] 能解释多表查询和聚合查询的结果来源。

## 本周范围

### 时光记录

第一版只保存文本，不处理图片和文件：

- 标题；
- 内容；
- 发生日期；
- 心情；
- 创建人；
- 情侣关系；
- 创建时间和更新时间。

### 纪念日

第一版支持：

- 标题；
- 纪念日期；
- 是否按年重复；
- 备注；
- 查询和排序。

### 首页汇总

只返回服务端已经有的数据：

- 情侣绑定信息；
- 在一起天数；
- 正在参加的挑战；
- 当前连续打卡天数；
- 即将到来的纪念日。

## 编写步骤

### 第 1 步：设计时光记录接口

先确认：

- 哪些字段由客户端提交；
- 创建人从哪里取得；
- 情侣关系从哪里取得；
- 列表的稳定排序是什么；
- 修改和删除权限如何判断。

### 第 2 步：完成记录 CRUD

遵循：

```text
请求参数校验
    ↓
取得当前用户和情侣关系
    ↓
执行业务权限判断
    ↓
调用 Mapper
    ↓
Entity 转 VO
```

### 第 3 步：完成纪念日查询

思考：

- 今年已经过去的纪念日如何处理；
- 按年重复的日期如何计算；
- 只查询未来一段时间时，条件如何表达；
- 日期比较使用数据库还是 Java 完成。

第一版选择一种主要方案并保持一致，不同时维护两套计算逻辑。

### 第 4 步：完成汇总查询

先明确首页需要的字段，再决定：

- 哪些数据可以复用已有 Service；
- 哪些数据需要新的聚合 SQL；
- 是否应该拆分成多次清晰查询，而不是一条难以维护的大 SQL。

## 验收矩阵

| 场景 | 预期结果 |
|---|---|
| 新增时光记录 | 当前情侣可见 |
| 查询时间线 | 分页、排序稳定 |
| 修改自己的记录 | 成功 |
| 修改伴侣的记录 | 按规则拒绝 |
| 删除不存在记录 | 404 |
| 查询纪念日 | 日期排序正确 |
| 查询即将到来的纪念日 | 返回符合日期范围的数据 |
| 首页汇总 | 各模块数据一致 |

## 周末复盘问题

1. 为什么创建人不能由前端提交并直接入库？
2. 时光记录列表的权限条件应该在哪一层组织？
3. 纪念日的周期计算属于哪一层？
4. 聚合查询返回的数据是否应该直接作为 Entity？
5. 如果首页需要五种数据，为什么不一定要拼成一条超复杂 SQL？
