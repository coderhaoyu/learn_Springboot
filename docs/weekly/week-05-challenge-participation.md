# 第 5 周：挑战与参与关系

> 建议投入：17–20 小时
> 对应总计划：[PLAN.md](../../PLAN.md)
> 完整产品设计：[couple-challenge-design.md](../couple-challenge-design.md)

## 当前目标

实现系统预置挑战和情侣参与关系，从单表 CRUD 进入“情侣—挑战”的业务关联。

```text
查询挑战目录
    ↓
查看挑战详情
    ↓
情侣加入挑战
    ↓
查询当前情侣参加的挑战
```

V1 暂时不做用户自定义挑战，先使用数据库初始化的系统挑战。

## 本周完成标准

- [ ] `challenges` 表字段和状态清晰；
- [ ] 能查询可参加挑战并分页；
- [ ] 能查询挑战详情；
- [ ] 当前情侣可以加入挑战；
- [ ] 同一情侣不能重复加入同一挑战；
- [ ] 尚未开始的挑战允许退出；
- [ ] 已开始或已结束的挑战不能随意退出；
- [ ] 非情侣用户不能代替其他情侣加入挑战；
- [ ] `couple_challenges` 的外键和唯一约束明确。

## 状态设计

挑战状态先控制在：

```text
PUBLISHED
ENDED
CANCELLED
```

参与状态先控制在：

```text
ONGOING
COMPLETED
ABANDONED
```

状态变化必须由 Service 根据当前状态判断，不能让客户端任意提交目标状态后直接覆盖。

## 编写步骤

### 第 1 步：设计挑战表

先回答：

- 目标天数由哪个字段表达？
- 开始和结束日期是否允许为空？
- 已结束挑战是否仍然可以查询？
- 系统挑战和未来用户创建挑战如何区分？

### 第 2 步：完成挑战查询

实现：

- 按状态查询；
- 分页；
- 稳定排序；
- 详情查询；
- 查询不存在挑战时的错误语义。

### 第 3 步：完成加入挑战

Service 流程：

```text
取得当前情侣
    ↓
查询挑战状态和日期
    ↓
查询是否已经参加
    ↓
写入参与关系
    ↓
返回参与结果
```

查重查询用于友好提示，数据库唯一约束用于最终一致性保护。

### 第 4 步：完成参与详情

返回当前情侣真正需要的字段：

- 挑战信息；
- 参与状态；
- 加入时间；
- 当前积分；
- 后续打卡进度占位信息。

不要直接暴露 Entity。

## 查询和索引思考

为以下查询草拟索引方案：

- 查询已发布挑战；
- 查询某个情侣参加的挑战；
- 判断某情侣是否已经加入某挑战；
- 查询某个挑战的参与情况。

先说明查询条件，再决定索引字段顺序。

## 验收矩阵

| 场景 | 预期结果 |
|---|---|
| 查询已发布挑战 | 分页成功 |
| 查看存在挑战 | 返回详情 |
| 查看不存在挑战 | 404 |
| 正常加入 | 成功创建参与关系 |
| 重复加入 | 409 |
| 未绑定情侣加入 | 409 或明确业务错误 |
| 非法状态退出 | 409 |
| 越权操作 | 403 |
