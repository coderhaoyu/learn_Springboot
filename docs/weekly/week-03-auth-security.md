# 第 3 周：认证与权限

> 建议投入：17–20 小时  
> 对应总计划：[PLAN.md](../../PLAN.md)

## 当前目标

实现注册、登录和当前用户接口，并用 Spring Security 与 JWT 保护业务接口。重点不是记住配置代码，而是理解一次带 Token 请求如何建立“当前用户身份”。

## 本周完成标准

- [ ] 注册时只保存 BCrypt 密码摘要。
- [ ] 登录校验成功后签发 JWT。
- [ ] `GET /api/users/me` 返回当前用户信息。
- [ ] 除注册和登录外，业务接口默认要求登录。
- [ ] 无 Token 或 Token 无效返回 401。
- [ ] 已登录但无权限访问资源时返回 403。
- [ ] 密码及其摘要不会出现在接口响应和日志中。

## 需要创建或调整的职责

- 认证 Controller：只处理注册、登录入口。
- 认证 Service：注册规则、密码校验、Token 签发。
- 注册/登录 DTO：限制客户端可提交的字段。
- 登录 VO：返回 Token 及必要信息。
- JWT 工具：生成、解析 Token。
- JWT 过滤器：读取请求头、解析身份、写入安全上下文。
- Security 配置：开放注册登录，其余接口默认认证。
- 用户 Mapper：按邮箱查询认证所需信息。

## 每日安排

### 周一：画认证数据流（2–3 小时）

1. 对比认证（你是谁）和授权（你能做什么）。
2. 设计注册、登录、当前用户三个接口。
3. 画出登录签发 Token 和后续携带 Token 的两条流程。
4. 确定 JWT 中只放稳定且必要的身份信息，例如用户 id。
5. 明确密码、密码摘要和 Token 的存放及返回边界。

### 周二：注册与密码摘要（3 小时）

1. 扩充 `users` 表以保存密码摘要。
2. 注册前检查邮箱业务冲突。
3. 使用 BCrypt 编码密码后再交给 Mapper。
4. 查询数据库，确认不是明文密码。
5. 检查用户 VO，确保不包含密码字段。

检查题：BCrypt 为什么不需要你单独保存盐值？密码为什么不能“解密”后比较？

### 周三：登录与 JWT 签发（3 小时）

1. 按邮箱查询用户。
2. 使用密码编码器比较原始密码与摘要。
3. 登录成功后生成包含过期时间的 Token。
4. 登录失败统一返回合适的认证错误，避免泄露邮箱是否存在。
5. 用一枚 Token 解码观察声明，但理解“可解码”不等于“可伪造”。

### 周四：JWT 过滤器与安全上下文（3 小时）

1. 从 `Authorization: Bearer <token>` 读取 Token。
2. 验证签名和过期时间。
3. 根据 Token 身份建立 Authentication。
4. 写入 SecurityContext。
5. 在 `/api/users/me` 读取当前用户 id，再由 Service 查询用户。

当天必须画出：过滤器在 Controller 之前如何工作。

### 周五：401、403 与安全规则（2–3 小时）

1. 开放注册、登录接口。
2. 其余业务接口默认要求认证。
3. 分别验证无 Token、错误 Token、过期 Token。
4. 构造一个“已认证但禁止访问”的规则，观察 403。
5. 统一认证与授权失败的 JSON 格式。

### 周六：完整认证流程联调（4–5 小时）

依次完成：注册 → 登录 → 保存 Token → 获取当前用户 → 携带 Token 访问用户业务接口 → 不带 Token 再次访问。

重点检查：

- 数据库是否只保存摘要。
- Token 过期时间是否合理。
- 响应和日志是否泄露秘密信息。
- 401 和 403 是否能够稳定区分。

### 周日：定向测试与复盘（2 小时）

覆盖注册成功、邮箱重复、登录成功、密码错误、缺少 Token、无效 Token和获取当前用户。只运行相关测试。

## 验收矩阵

| 场景 | 预期结果 |
|---|---|
| 注册成功 | 密码摘要入库，响应无密码字段 |
| 邮箱重复 | 409 |
| 登录成功 | 返回可用于后续请求的 JWT |
| 密码错误 | 401，不泄露具体账号信息 |
| 无 Token 访问业务接口 | 401 |
| 已登录但权限不足 | 403 |
| 携带合法 Token 获取自己 | 返回当前用户 VO |

## 周末复盘问题

1. JWT 的签名、载荷、过期时间分别解决什么问题？
2. 为什么 JWT 可以被客户端看到，却不能被客户端任意修改？
3. 过滤器、Controller、Service 的执行顺序是什么？
4. 为什么从 Token 得到用户 id 后，通常仍要查询数据库？
5. 401 与 403 的判断前提有什么不同？
