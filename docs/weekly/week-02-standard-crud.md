# 第 2 周：规范接口与异常

> 建议投入：15–18 小时
> 对应总计划：[PLAN.md](../../PLAN.md)

## 当前目标

把用户 CRUD 从“能运行”整理成可供未来前端消费的稳定接口，明确输入、输出、状态码和错误语义。

```text
请求格式 → DTO 校验 → Service 业务判断 → Entity 持久化 → VO 响应
```

## 本周完成标准

- [ ] 新增、修改和查询参数都有清晰 DTO；
- [ ] Entity 不直接作为对外响应；
- [ ] `@Valid`、`@Validated` 能处理请求体和查询参数；
- [ ] 用户列表支持稳定分页；
- [ ] 参数错误返回 400；
- [ ] 用户不存在返回 404；
- [ ] 邮箱冲突返回 409；
- [ ] 全局异常处理不在每个 Controller 中重复 `try/catch`；
- [ ] 相关测试只针对用户模块和受影响的通用类。

## 需要检查的职责

- Controller：接收请求、绑定参数、调用 Service、返回结果；
- Service：查重、存在性、业务规则和 Entity/VO 转换；
- Mapper：SQL、参数绑定和结果映射；
- DTO：限制客户端输入并承载校验；
- VO：控制未来前端能够看到的字段；
- 全局异常处理：把异常翻译成 HTTP 响应。

## 编写步骤

### 第 1 步：画出接口边界

对每个用户接口记录：

- 请求方法和路径；
- 路径参数、查询参数和请求体；
- 成功状态码和响应结构；
- 参数错误、资源不存在和业务冲突；
- 前端需要哪些字段，哪些字段不能返回。

### 第 2 步：检查 DTO、Entity 和 VO

回答：

```text
前端允许提交哪些字段？
数据库实际保存哪些字段？
响应需要展示哪些字段？
```

不要为了形式复制大量内容相同的类。只有当输入和输出边界确实不同，才保留独立对象。

### 第 3 步：完善校验

覆盖：

- 必填文本；
- 邮箱格式；
- 年龄范围；
- 页码和每页条数；
- 路径参数和查询参数。

区分两类判断：

- 格式不合规：进入业务前即可判断；
- 业务不允许：由 Service 根据数据库状态判断。

### 第 4 步：整理异常响应

统一确认：

```text
400：请求格式或参数不合法
404：目标用户不存在
409：邮箱等业务数据冲突
500：未预期的系统错误
```

## 验收矩阵

| 场景 | 预期结果 |
|---|---|
| 合法新增 | 成功，响应不泄露内部字段 |
| 空姓名或非法邮箱 | 400 |
| 查询不存在用户 | 404 |
| 新增重复邮箱 | 409 |
| 分页参数不合法 | 400 |
| 未知异常 | 500，保留日志定位线索 |

## 周末复盘问题

1. 为什么邮箱格式错误是 400，而邮箱重复是 409？
2. 为什么 Controller 不负责邮箱查重？
3. 为什么 Entity 不应该直接作为所有接口响应？
4. 为什么数据库唯一约束仍然不能被 Service 查重替代？
5. 如果两个重复邮箱请求同时到达，当前实现还缺少哪一道防线？
