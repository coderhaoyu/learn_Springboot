# 第 2 周：把 CRUD 做成规范接口

> 日期：2026 年 8 月 17–23 日  
> 建议投入：16–20 小时  
> 对应总计划：[PLAN.md](../../PLAN.md)

## 当前目标

在数据库 CRUD 已经跑通的基础上，补齐接口边界、分页和异常体系，让客户端能稳定地区分成功、参数错误、资源不存在与业务冲突。

## 本周完成标准

- [ ] 新增和修改使用独立 DTO，响应使用 VO，不直接暴露 Entity。
- [ ] 姓名、年龄、邮箱等请求字段具备 Bean Validation 规则。
- [ ] 用户列表支持 `page`、`size` 分页，并返回总数。
- [ ] 普通接口统一使用 `ApiResponse<T>`。
- [ ] 分页统一使用 `PageResult<T>`。
- [ ] 参数错误返回 400，用户不存在返回 404，邮箱冲突返回 409。
- [ ] Controller 中没有业务规则，Service 中没有 HTTP 响应拼装。

## 需要创建或调整的文件

- `user/dto`：创建用户 DTO、更新用户 DTO、分页查询 DTO。
- `user/vo`：用户 VO。
- `common/response`：`ApiResponse<T>`、`PageResult<T>`。
- `common/exception`：业务异常、错误码或错误信息定义、全局异常处理器。
- `UserController`：参数接收、校验与响应。
- `UserService`：邮箱冲突和数据存在性等业务规则。
- `UserMapper` 与 XML：分页查询、总数查询、按邮箱查询。

如果决定把现有包结构迁移为按业务模块组织，本周只迁移用户相关类，不创建尚未使用的空目录。

## 每日安排

### 8 月 17 日（周一）：复盘接口并设计边界（2–3 小时）

1. 列出五个用户接口的路径、方法、请求参数和响应字段。
2. 区分 Entity、DTO、VO 的职责，确定哪些字段不能由客户端提交或不能返回。
3. 设计成功响应和错误响应的 JSON 形状。
4. 画出“参数格式校验”和“业务规则校验”所在层级。

当天产出：接口表、DTO/VO 字段表、响应样例。先完成设计，不急着编码。

### 8 月 18 日（周二）：DTO、VO 与参数校验（3 小时）

1. 为新增和修改分别创建 DTO，不为了复用强行合并不同语义。
2. 使用校验注解表达必填、长度、范围和邮箱格式。
3. Controller 使用 `@Valid` 触发请求体校验。
4. 在 Service 或明确的转换位置完成 DTO、Entity、VO 转换。
5. 用合法和非法请求各验证一次。

检查题：为什么“邮箱格式不正确”属于 400，而“邮箱已存在”属于 409？

### 8 月 19 日（周三）：分页查询（3 小时）

1. 约定页码从 1 开始，确定默认 `page` 和 `size`。
2. 写出 `offset = (page - 1) × size`，用三组数据手算验证。
3. Mapper 分别执行分页数据查询和总数查询。
4. Service 组装 `PageResult<UserVO>`。
5. 测试第一页、中间页和超过最后一页的请求。

当天产出：分页参数说明、两条 SQL 的职责说明、分页响应样例。

### 8 月 20 日（周四）：业务异常与全局异常处理（3 小时）

1. 定义“用户不存在”和“邮箱已存在”两类业务结果。
2. Service 在对应业务点抛出异常。
3. 使用全局异常处理器映射 404、409。
4. 将 Bean Validation 错误映射为 400，并返回可读的字段信息。
5. 保留未知程序错误的 500 语义，不静默吞掉异常。

检查题：为什么不在每个 Controller 方法里重复 `try/catch`？

### 8 月 21 日（周五）：统一响应与职责检查（2–3 小时）

1. 普通成功结果包装为 `ApiResponse<T>`。
2. 分页数据放入 `PageResult<T>`，避免 Controller 手工计算分页信息。
3. 逐个检查 Controller 是否出现邮箱查重、对象查询或 SQL 相关逻辑。
4. 逐个检查 Service 是否依赖 HTTP 专用对象。
5. 验证 JSON 字段命名在所有接口中一致。

### 8 月 22 日（周六）：端到端场景验证（4–5 小时）

按顺序验证：

- 新增合法用户。
- 使用同一邮箱再次新增。
- 使用非法邮箱、空姓名、越界年龄新增。
- 查询存在和不存在的用户。
- 修改存在和不存在的用户。
- 分页查询不同页码。
- 删除用户后再次查询。

每个场景记录请求、状态码、响应和数据库结果。

### 8 月 23 日（周日）：相关测试与复盘（2 小时）

2. 不运行无关的项目级检查。
3. 对比格式校验、业务校验和数据库约束失败时的调用路径。

## 验收矩阵

| 场景 | 状态码 | 关键检查 |
|---|---:|---|
| 新增成功 | 2xx | 返回 VO，不包含内部字段 |
| 请求字段非法 | 400 | 明确指出非法字段 |
| 用户不存在 | 404 | Service 判定业务结果 |
| 邮箱重复 | 409 | Service 校验与唯一约束共同保护 |
| 分页成功 | 200 | 包含列表、总数、页码和每页条数 |

## 学习重点

- DTO/VO 是服务端接口边界，不只是复制 Entity。
- 参数校验解决“格式是否合规”，Service 解决“业务是否允许”。
- 唯一约束是数据一致性的最后防线，不能只依赖先查后写。
- 全局异常处理把 Java 异常统一翻译为 HTTP 语义。
