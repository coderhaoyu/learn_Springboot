# 第 6 周：测试、SQL 与工程质量

> 建议投入：18–20 小时  
> 对应总计划：[PLAN.md](../../PLAN.md)

## 当前目标

为已经完成的核心业务建立有层次的测试保障，检查关键 SQL 的执行计划，引入数据库版本迁移，并形成可重复的问题定位流程。本周以验证和修正为主，不扩展新业务模块。

## 本周完成标准

- [ ] Mapper 测试验证关键 SQL、参数绑定和结果映射。
- [ ] Service 测试验证业务规则、权限、乐观锁与事务。
- [ ] MockMvc 测试验证请求校验、状态码、JSON 和安全规则。
- [ ] 必测场景全部有明确的测试归属。
- [ ] 使用 `EXPLAIN` 检查项目分页和任务组合筛选。
- [ ] 使用数据库版本迁移工具从空库创建所需表结构。
- [ ] 能从日志中找到第一个有效异常与最底层 `Caused by`。
- [ ] 所有检查按相关文件或相关测试定向执行，不触发无关的全项目检查。

## 测试分层原则

| 层级 | 主要验证 | 不应重复承担 |
|---|---|---|
| Mapper | SQL、绑定、映射、真实数据库约束 | Service 业务分支 |
| Service | 业务规则、权限、事务、依赖协作 | HTTP JSON 细节 |
| MockMvc | 路由、校验、状态码、响应 JSON、安全入口 | 每条 SQL 的内部实现 |

先把测试放在最能准确发现问题的层级，避免每个场景都写成昂贵的全链路测试。

## 必须覆盖的场景

- 注册成功、邮箱重复。
- 登录成功、密码错误。
- 用户和项目不存在。
- 非成员访问项目、普通成员管理成员。
- 创建项目的第二步失败后事务回滚。
- 任务分页及状态、负责人、优先级组合筛选。
- 两个请求使用相同任务版本发生乐观锁冲突。
- Bean Validation 参数校验失败。

## 每日安排

### 周一：测试盘点与用例设计（3 小时）

1. 列出现有接口、核心 Service 方法和复杂 SQL。
2. 将必测场景分配给 Mapper、Service 或 MockMvc。
3. 为每个用例写出准备数据、操作、预期结果和清理方式。
4. 确定测试数据库方案，确保不会误操作开发数据。
5. 建立测试完成矩阵，不用测试数量代替有效覆盖。

当天产出：一份按层级分类的测试清单。

### 周二：Mapper 测试（3 小时）

1. 验证用户按邮箱查询和唯一约束。
2. 验证项目成员关系查询不会返回重复项目。
3. 验证任务组合筛选的数据列表和总数一致。
4. 验证下划线列名到 Java 属性的结果映射。
5. 每个测试独立准备所需最小数据，避免依赖执行顺序。

检查题：Mapper 测试为什么应尽量连接真实关系型数据库，而不是模拟 Mapper 自己？

### 周三：Service 测试（3 小时）

1. 覆盖邮箱重复、用户不存在等业务分支。
2. 覆盖负责人、成员、非成员的权限规则。
3. 覆盖任务负责人不属于项目和非法状态流转。
4. 覆盖更新影响 0 行时的乐观锁冲突。
5. 对事务用例验证最终数据库状态，而不仅是异常是否抛出。

### 周四：MockMvc 与安全测试（3 小时）

1. 覆盖请求体字段非法、缺少必要参数和分页参数错误。
2. 验证 400、401、403、404、409 的状态码与响应格式。
3. 覆盖注册、登录和获取当前用户。
4. 覆盖一条合法 Token 请求与一条无 Token 请求。
5. JSON 断言只检查接口契约所需字段，避免与内部实现紧耦合。

### 周五：EXPLAIN 与索引（3 小时）

1. 为表准备具有区分度的测试数据，避免用几行数据得出武断结论。
2. 对项目分页 SQL 执行 `EXPLAIN`。
3. 对任务常见组合筛选 SQL 执行 `EXPLAIN`。
4. 记录访问类型、可能使用的索引、实际选择的索引和扫描行数估计。
5. 对比添加或调整索引前后的执行计划。
6. 保留真正服务查询的索引，避免为所有字段单独建索引。

### 周六：数据库迁移与空库演练（4–5 小时）

1. 选择一个数据库迁移工具，并理解版本脚本只向前演进的原则。
2. 把 users、projects、project_members、tasks 的结构整理为有顺序的迁移。
3. 新建空数据库，让应用通过迁移创建全部结构。
4. 启动应用并跑通最小业务流程。
5. 再次启动，确认已执行的版本不会重复破坏数据。
6. 故意制造一次迁移错误，练习从日志中定位脚本和 SQL 行。

### 周日：集中回归与调试复盘（2–3 小时）

1. 按测试矩阵定向运行相关测试。
2. 修复失败时记录：现象、首个有效异常、底层原因、涉及层级、修改和验证。
3. 选一个 Controller 错误、一个 Service 错误和一个 SQL 错误，说明测试如何定位它们。
4. 统计尚未覆盖的高风险规则，而不是只统计测试方法数量。

## 学习重点

- 不同层次的测试保护不同边界，测试放错层会变慢且难定位。
- 事务测试必须观察最终数据状态。
- `EXPLAIN` 是理解访问路径的入口，不等同于真实生产性能结论。
- 数据库迁移使表结构变化可追踪、可复现，替代手工维护某台数据库。
- 调试应优先寻找根因链，而不是只看最后一行或最外层异常。

## 周末复盘问题

1. Mapper、Service、MockMvc 测试分别最擅长发现什么问题？
2. 为什么测试不能共享一组会被不断修改的数据？
3. 事务回滚测试只断言抛出异常为什么不够？
4. `EXPLAIN` 中全表扫描一定错误吗？还需要考虑哪些条件？
5. 数据库迁移脚本为什么不建议修改已经在其他环境执行过的版本？
