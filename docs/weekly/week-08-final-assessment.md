# 最终验收：独立完成任务评论模块

> 建议投入：每天 4–6 小时  
> 对应总计划：[PLAN.md](../../PLAN.md)

## 验收目标

不参考现成业务实现，在三天内独立完成“任务评论”模块，用它验证自己是否已经能够完成从需求、设计、编码、测试到文档的完整后端开发闭环。

本文件只定义要求、推进顺序和验收标准，不给出最终表结构、方法实现或完整 SQL。

## 固定业务规则

- 项目成员可以在该项目的任务下发表评论。
- 评论作者可以删除自己的评论。
- 非项目成员不能查看或新增评论。
- 非评论作者不能删除评论。
- 评论必须关联一个存在的任务和一个作者。
- 评论接入现有认证、统一响应和异常体系。

## 必须独立决定的内容

- 表名、主键和字段类型。
- 任务与评论、用户与评论之间的外键。
- 应添加哪些索引，以及每个索引服务哪条查询。
- 新增、列表、删除接口的路径、请求和响应。
- Controller、Service、Mapper、DTO、VO 的职责与命名。
- 删除不存在评论、无权删除评论时分别返回什么状态码。
- 删除采用物理删除还是逻辑删除，并说明选择理由。
- 测试数据如何准备和隔离。

## 验收前纪律

- 先提交设计草图，再开始编码。
- 每次只完成一个接口闭环。
- 遇到错误先记录日志和调用栈，再修改。
- Agent 只负责评审、追问和分层提示，不直接生成完整模块。
- 不为了赶时间引入 MyBatis-Plus、代码生成器或新的复杂框架。
- 只运行与评论模块及受影响文件相关的检查和测试。

## 第 1 天：独立设计与打通新增

### 当前目标

完成需求澄清、表结构、API、分层设计和数据库迁移，并打通新增评论的最小闭环。

### 编写步骤

1. 用自己的话重述业务规则，列出允许和禁止的操作。
2. 画出 `users → projects → tasks → comments` 的关系。
3. 设计评论表的字段、外键、非空约束和索引。
4. 设计新增、列表、删除三个接口。
5. 列出需要创建的 Entity、DTO、VO、Controller、Service、Mapper/XML。
6. 为每个类写一句职责，检查是否存在职责重复。
7. 编写数据库迁移并在空库验证。
8. 从新增评论开始实现完整链路。
9. 验证项目成员新增成功、非成员新增失败、任务不存在。

### 当天产出

- [ ] 一张关系图。
- [ ] 一份字段与索引说明。
- [ ] 一份 API 契约。
- [ ] 一份分层职责清单。
- [ ] 可执行的数据库迁移。
- [ ] 新增评论接口最小闭环。

### 当天自检

1. 能否解释每个外键保护了什么关系？
2. 能否说明列表查询将使用哪个索引？
3. 新增权限是在 Controller、Service 还是 Mapper 判断？为什么？
4. 响应是否避免直接暴露 Entity？

## 第 2 天：列表、删除与异常场景

### 当前目标

完成评论列表与删除，接入项目成员权限和作者权限，并补齐所有主要错误场景。

### 编写步骤

1. 完成按任务查询评论列表，确定稳定排序规则。
2. 返回评论作者所需的展示字段，避免不必要的用户信息。
3. 查询前验证任务及当前用户的项目成员关系。
4. 完成删除评论，并验证当前用户是评论作者。
5. 区分评论不存在、任务不存在、非项目成员和非作者。
6. 将错误接入既有 404、403 等响应体系。
7. 用作者、其他成员、非成员三种身份逐项验证。
8. 检查 Controller 无业务判断，Service 无 HTTP 响应拼装，Mapper 只负责数据访问。

### 当天产出

- [ ] 评论列表接口。
- [ ] 评论删除接口。
- [ ] 权限场景验证表。
- [ ] 错误状态码记录。
- [ ] 一份当天 Debug 记录，包含根因和验证过程。

### 权限验收矩阵

| 操作 | 评论作者 | 其他项目成员 | 非项目成员 |
|---|---:|---:|---:|
| 新增评论 | 允许 | 允许 | 禁止 |
| 查看评论 | 允许 | 允许 | 禁止 |
| 删除该评论 | 允许 | 禁止 | 禁止 |

### 当天自检

1. 权限判断是否依赖客户端提交的作者 id？如果是，设计有问题。
2. 列表 SQL 是否可能因为关联查询产生重复评论？
3. 删除操作如何确认目标评论确实存在且属于当前用户？
4. 非作者删除返回 403，而评论不存在返回 404 的依据是什么？

## 第 3 天：测试、文档与最终答辩

### 当前目标

完成相关测试、空库验证、文档更新和完整业务演示，并能脱离代码解释整个模块。

### 测试步骤

1. Mapper：验证新增、按任务列表、删除及必要的结果映射。
2. Service：验证成员新增、非成员拒绝、作者删除、其他成员禁止删除。
3. MockMvc：验证请求校验、认证、403、404 和响应 JSON。
4. 从空数据库运行迁移并启动应用。
5. 只运行评论模块和受影响功能的定向测试。
6. 记录失败用例的第一个有效异常和根本原因。

### 文档步骤

1. 更新数据库关系图。
2. 更新核心接口说明和状态码。
3. 在完整业务流程中加入“发表评论、查看评论、删除评论”。
4. 确认 README 的启动步骤仍能从空环境执行。

### 最终演示流程

1. 注册并登录用户 A、B、C。
2. A 创建项目和任务，并添加 B 为成员；C 保持为非成员。
3. A、B 分别发表评论。
4. B 查看任务的评论列表。
5. C 尝试查看或新增评论，确认被拒绝。
6. B 尝试删除 A 的评论，确认被拒绝。
7. A 删除自己的评论并再次查询列表。
8. 检查数据库最终状态与接口结果一致。

## 最终口述题

不看代码，逐题回答：

1. 一次新增评论请求如何从 HTTP 到 MySQL 再返回 JSON？
2. 当前用户身份从哪里获得，为什么不能相信请求体中的用户 id？
3. 如何确认评论所属任务对应的项目成员关系？
4. DTO、VO、Entity 在评论模块中分别解决什么问题？
5. Mapper 参数如何进入 SQL，查询结果如何变成 Java 对象？
6. 为什么权限检查属于 Service 业务规则？
7. 哪些错误是 400、401、403、404？
8. 评论列表的索引为什么这样设计？
9. 哪些测试放在 Mapper、Service、MockMvc，为什么？
10. 如果接口返回 500，你会如何沿异常链定位？
