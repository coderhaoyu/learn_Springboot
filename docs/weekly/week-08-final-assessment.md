## 当前目标

对后端整体质量负责，并独立完成“成就”扩展模块，验证自己是否能够从需求、表结构、接口、分层、测试到文档完成一个小型功能闭环。

## 一、整体质量收尾

### 测试范围

只运行和本项目相关的定向检查，覆盖：

- 用户 Mapper 和 Service；
- 注册、登录和当前用户；
- 情侣绑定的成功和失败场景；
- 挑战加入和退出；
- 重复打卡和并发一致性；
- 时光记录权限；
- 纪念日查询；
- 全局异常和响应 JSON。

### SQL 和数据库检查

- 从空数据库执行初始化脚本；
- 检查外键、唯一约束和必要索引；
- 对挑战、打卡和时间线查询使用 `EXPLAIN`；
- 确认事务失败时没有残留半成品数据；
- 确认密码和秘密配置没有进入仓库。

### 交付检查

- 开发、测试配置分离；
- Docker Compose 可以启动应用和 MySQL；
- README 包含启动、数据库和接口验证步骤；
- 数据关系图和接口文档与实现一致；
- 日志可以帮助定位首个有效异常和 `Caused by`。

## 二、独立完成：成就模块

不参考现成业务实现，独立完成以下后端功能：

### 业务要求

- 系统有若干预置成就，例如“连续打卡 7 天”；
- 情侣可以查询已解锁和待解锁成就；
- 达到条件后解锁成就；
- 同一个情侣的同一个成就只能解锁一次；
- 非情侣成员不能查看成就；
- 成就解锁不能因为重复请求而产生重复记录。

### 设计要求

先自己确定：

1. `achievements` 和 `couple_achievements` 的字段；
2. 成就与情侣、挑战、打卡之间的关系；
3. 查询已解锁和待解锁的 API；
4. 成就判断放在哪个 Service；
5. 唯一约束和事务边界；
6. 需要哪些 DTO、VO、Mapper 和测试。

不要直接复制其他模块的实现。可以复用项目已有的响应、异常和认证基础，但业务流程必须自己设计。

## 三天安排

### 第 1 天：需求、表结构和查询

- 画数据关系；
- 写字段、状态、约束和索引；
- 设计列表和详情接口；
- 先用文字写出成就解锁伪代码；
- 让 Agent 先评审设计，不直接生成完整实现。

### 第 2 天：Service、Mapper 和接口

- 自己完成分层；
- 接入当前用户和情侣权限；
- 实现成就查询；
- 实现解锁规则；
- 验证重复请求和不存在数据。

### 第 3 天：测试、文档和答辩

- 补充 Mapper、Service 和 MockMvc 定向测试；
- 从空数据库验证；
- 更新接口说明和关系图；
- 演示完整业务流程；
- 回答最终口述题。

## 最终验收流程

1. 注册用户 A 和 B；
2. A、B 完成情侣绑定；
3. 情侣加入一个挑战；
4. 完成若干天打卡；
5. 达到成就条件；
6. 查询成就列表；
7. 重复触发解锁，确认没有重复记录；
8. 使用非情侣用户访问，确认被拒绝；
9. 检查数据库状态和接口响应一致。

## 最终口述题

1. 一次共同打卡请求如何从 HTTP 到 MySQL 再返回 JSON？
2. 当前用户身份从哪里获得，为什么不能相信请求体中的用户 id？
3. 如何判断用户是否属于某个情侣关系？
4. DTO、Entity 和 VO 分别解决什么问题？
5. 为什么重复打卡需要数据库唯一约束？
6. 事务和唯一约束分别解决什么问题？
7. 什么是丢失更新，如何验证和处理？
8. 为什么成就解锁需要幂等设计？
9. 哪些测试应该放在 Mapper、Service 和 MockMvc？
10. 如果接口返回 500，你会如何沿异常链定位根因？
