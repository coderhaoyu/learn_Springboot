# users 表设计

## 1. 业务目的

`users` 表用于保存系统用户的基础信息，支持用户新增、查询、修改和删除。

当前阶段保存：

- 用户编号
- 用户姓名
- 用户年龄
- 用户邮箱
- 创建时间
- 更新时间

## 2. 字段设计

| 字段         | 类型           | 允许为空 | 约束         | 说明             |
|--------------|----------------|---------:|--------------|------------------|
| `id`         | `BIGINT`       |       否 | 主键、自增   | 用户唯一编号     |
| `name`       | `VARCHAR(50)`  |       否 |              | 用户姓名         |
| `age`        | `INT`          |       否 |              | 用户年龄         |
| `email`      | `VARCHAR(254)` |       否 | 唯一         | 用户邮箱         |
| `created_at` | `DATETIME`     |       否 | 默认当前时间 | 用户创建时间     |
| `updated_at` | `DATETIME`     |       否 | 自动更新时间 | 用户最后修改时间 |

## 3. 设计决策

### 3.1 为什么使用 BIGINT 自增主键？

`id` 是用户在数据库中的唯一标识。

选择 `BIGINT` 的原因：

1. 能保存非常多的数据；
2. Java 的 `Long` 可以直接对应 MySQL 的 `BIGINT`；
3. 自增可以由数据库自动生成，不需要客户端提交；
4. 避免客户端伪造或重复主键。

所以新增用户时，客户端只提交姓名、年龄和邮箱，数据库负责生成 `id`。

### 3.2 为什么邮箱需要数据库唯一约束？

业务上要求同一个邮箱只能对应一个用户。

Service 可以先查询邮箱是否存在，但这不是最后防线：

```text
请求 A：查询邮箱不存在
请求 B：查询邮箱不存在
请求 A：插入邮箱
请求 B：插入邮箱
```

两个请求可能同时通过 Java 检查，最终产生重复数据。

因此需要数据库的 `UNIQUE` 约束。数据库会在最终写入时保证唯一性，即使并发请求同时到达，也不会允许重复邮箱。

### 3.3 时间字段由谁维护？

本项目选择由数据库维护：

- `created_at`：插入时自动设置当前时间；
- `updated_at`：插入和更新时由数据库自动维护。

这样做的好处是：

1. 所有写入来源使用同一套时间规则；
2. Java 代码不需要重复设置时间；
3. 即使以后有脚本或其他程序写数据库，时间字段仍然统一。

## 4. 索引设计

当前阶段需要：

- `PRIMARY KEY (id)`：支持按用户编号查询；
- `UNIQUE (email)`：保证邮箱唯一，并支持按邮箱查询。

暂时不为 `name` 和 `age` 单独建立索引，因为当前没有明确的高频筛选需求。

## 5. 与 Java 对象的对应关系

| 数据库字段   | Java 属性        |
|--------------|------------------|
| `id`         | `Long id`        |
| `name`       | `String name`    |
| `age`        | `Integer age`    |
| `email`      | `String email`   |
| `created_at` | 后续增加时间属性 |
| `updated_at` | 后续增加时间属性 |

数据库使用下划线命名，Java 使用小驼峰命名。MyBatis 需要通过别名或结果映射完成转换。
