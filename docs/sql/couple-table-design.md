# 情侣关系表设计（couples 与 couple_invitations）

## 1. 业务目的

这两张表支撑第 4 周的核心业务：把两个独立注册的用户，绑定成一段情侣关系。

完整流程如下（小 A 邀请小 B）：

1. 小 A 注册、登录；
2. 小 B 注册、登录；
3. 小 A 点击「邀请伴侣」，后端生成邀请码，例如 `7F3K9M`；
4. **小 A 通过微信等方式把邀请码发给小 B**；
5. 小 B 在应用内输入 `7F3K9M` 并确认；
6. 后端校验这个邀请码能否使用；
7. 校验通过，关系成立；
8. 之后双方都能查询到对方。

### 1.1 为什么需要邀请码

第 4 步不经过后端。服务器完全不知道这次传递发生过。

这正是邀请码存在的理由：本产品是私密应用，两个用户在系统内搜索不到彼此，也不应该能搜到。邀请码的作用是把线下已经存在的信任关系带进系统——谁手上有这个码，就说明是邀请人亲自给的。

### 1.2 为什么是两张表

流程里有两个时刻必须写数据库：

- **第 3 步**：邀请码必须存下来，否则第 6 步无法校验；
- **第 7 步**：关系成立的事实必须存下来，否则第 8 步查不到伴侣。

这两个时刻的性质完全不同：

| | 第 3 步 | 第 7 步 |
|---|---|---|
| 记录的是 | 一个过程 | 一个结果 |
| 生命周期 | 会过期、用完即废 | 一旦成立长期有效 |
| 对应表 | `couple_invitations` | `couples` |

分成两张表不是形式要求，是这条流程本身包含两件不同的事。

## 2. 绑定时的校验清单

第 6 步需要做的判断，共 6 条。

关于邀请码本身：

1. 这个码存在吗；
2. 这个码过期了吗；
3. 这个码被用过了吗。

关于人：

4. 输码的人是不是发码的人自己；
5. 发码人现在还是单身吗；
6. 输码人现在是单身吗。

另外第 3 步发码时也有一条判断：当前用户已有有效关系时，不允许发起邀请。

### 2.1 第 5 条最容易被漏掉

「码是邀请人自己发的，为什么还要检查邀请人」——因为时间差：

```text
周一：小 A 生成 7F3K9M，发给小 B
周三：小 A 又生成一个码给小 C，小 C 绑定成功
周四：小 B 才看到消息，输入 7F3K9M
```

周四这一刻，`7F3K9M` 本身完全正常：没过期、没用过、小 B 也不是小 A，前 3 条校验全部通过。但小 A 已经和小 C 在一起了。

**邀请码里存的是「签发那一刻的状态」，要判断的是「使用这一刻的状态」。** 这两件事必须分开查，凭证信息不能代替对当前状态的实时检查。

同样的问题在 JWT 上也存在：token 签发时用户存在，使用时用户可能已被删除。

### 2.2 校验涉及的数据来源

| 判断 | 数据来源 |
|---|---|
| 1、2、3 | `couple_invitations` |
| 4 | 两个 id 直接比较，不查库 |
| 5、6 | `couples` |

## 3. `couples` 表

### 3.1 一行代表一段关系

`users` 表里一行是一个人；`couples` 表里**一行是一段关系**。

两个人共用一行，不是各存一行。一个用户在这张表里，要么完全不出现，要么出现在某一行的某一列。

### 3.2 字段设计

| 字段 | 类型 | 允许为空 | 约束 | 说明 |
|---|---|---:|---|---|
| `id` | `BIGINT` | 否 | 主键、自增 | 关系编号，后续挑战、打卡、时光记录都关联它 |
| `user_a_id` | `BIGINT` | 否 | | 关系一方，存 id 较小的用户 |
| `user_b_id` | `BIGINT` | 否 | | 关系另一方，存 id 较大的用户 |
| `status` | `VARCHAR(20)` | 否 | | 关系状态：`ACTIVE` / `ENDED` |
| `bound_at` | `DATETIME` | 否 | | 绑定成功时间，首页「在一起天数」使用 |
| `created_at` | `DATETIME` | 否 | 默认当前时间 | 记录创建时间 |
| `updated_at` | `DATETIME` | 否 | 自动更新 | 记录最后修改时间 |

两个用户列使用 `BIGINT`，必须与 `users.id` 类型完全一致，否则无法建立外键，索引也可能失效。

### 3.3 为什么列名是 a / b，不是 inviter / accepter

绑定完成后，谁发起邀请对业务已无意义，双方在关系中完全对等。命名里带 `inviter` 会误导出「邀请人有特权」的逻辑。

更重要的原因见 3.5：这两列的顺序由 id 大小决定，与谁发起邀请无关。

### 3.4 为什么需要 status，而不是分手就删行

业务上的「结束关系」，在数据库里不是 `DELETE`。

关系存续期间，大量数据通过 `couple_id` 关联到这一行：参加过的挑战、每天的打卡记录、写过的时光记录、解锁的成就。删掉 `couples` 的这一行，这些记录会全部指向一个不存在的关系。

所以分手是**把 status 改成 `ENDED`**，历史行保留。

由此，「查某人是否单身」的条件必须是：

```text
这个用户出现在 user_a_id 或 user_b_id
且 status = 'ACTIVE'
```

表里会同时存在有效和已结束的关系行，只判断「有没有这一行」是不够的。

一般规律：业务上的「结束」「取消」「注销」，绝大多数在数据库里都是状态变更，不是删除。真正的删除只用于「这行数据本来就不该存在」。

### 3.5 防止同一对用户出现两行

要防的坏数据：

| id | user_a_id | user_b_id |
|---|---|---|
| 1 | 1 | 2 |
| 2 | 1 | 2 |

由数据库唯一约束负责：

```text
UNIQUE (user_a_id, user_b_id)
```

但唯一约束只认「列的组合」。如果这次由小 B 发起邀请，代码会插入 `(2, 1)`，数据库视为不同组合，约束不报错，同一对用户又变成两行。

因此约定：**写入前永远把 id 较小的用户放在 `user_a_id`。**

这样同一对用户不论谁发起邀请，落库形式唯一，唯一约束才真正生效。这条规范化规则必须在 Service 写入前执行。

### 3.6 「一个用户最多一段有效关系」：数据库不兜底

要防的坏数据：

| id | user_a_id | user_b_id |
|---|---|---|
| 1 | 1 | 2 |
| 2 | 1 | 3 |

`UNIQUE (user_a_id, user_b_id)` 挡不住，因为 `(1,2)` 和 `(1,3)` 确实是不同组合。

换任何唯一约束也表达不了这条规则。需要表达的是「某个 id 不许在有效行的两列的任意位置出现第二次」，这不属于「组合不重复」，唯一约束做不到。

**结论：这条规则只能由 Service 在绑定前查询保证，数据库没有任何兜底。**

已知漏洞：

```text
请求 X：查小 B → 单身
请求 Y：查小 B → 单身
请求 X：插入 (2, 5)
请求 Y：插入 (2, 9)   ← 小 B 出现两段有效关系
```

与 `users` 表邮箱重复的并发交错（见 [user-table-design.md](user-table-design.md) 3.2）形状相同，区别是邮箱有 `UNIQUE(email)` 作为最终防线，这条规则没有。

当前版本接受这个风险：正常使用下不会触发。真正的处理放在第 6 周并发一致性阶段。

### 3.7 索引设计

- `PRIMARY KEY (id)`；
- `UNIQUE (user_a_id, user_b_id)`：保证同一对用户唯一；
- `user_b_id` 单列索引：查询「某人是否有有效关系」的条件是 `user_a_id = ? OR user_b_id = ?`，唯一约束的最左列已经覆盖 `user_a_id`，`user_b_id` 需要单独索引才能走上。

## 4. `couple_invitations` 表

### 4.1 字段由校验清单反推

字段不是凭感觉列举的，而是从第 2 节的判断反推出来的：

| 要判断的事 | 需要的字段 |
|---|---|
| 码存在吗 | `code` |
| 码过期了吗 | `expires_at` |
| 码用过了吗 | `status` |
| 输码人是不是发码人自己 | `inviter_id` |

### 4.2 字段设计

| 字段 | 类型 | 允许为空 | 约束 | 说明 |
|---|---|---:|---|---|
| `id` | `BIGINT` | 否 | 主键、自增 | 邀请编号 |
| `inviter_id` | `BIGINT` | 否 | | 邀请发起人 |
| `code` | `CHAR(6)` | 否 | 唯一 | 邀请码 |
| `expires_at` | `DATETIME` | 否 | | 过期时间，签发时间 + 24 小时 |
| `status` | `VARCHAR(20)` | 否 | | `PENDING` / `USED` |
| `used_at` | `DATETIME` | 是 | | 被使用的时间，便于排查问题 |
| `created_at` | `DATETIME` | 否 | 默认当前时间 | 签发时间 |
| `updated_at` | `DATETIME` | 否 | 自动更新 | 最后修改时间 |

### 4.3 code 必须唯一

绑定时要用 `code` 查出唯一一行。若表中存在两行相同的 code，无法确定该用哪一行。与 `users.email` 同理。

### 4.4 「过期」不是状态，是算出来的

状态很容易被设计成三个值：未使用 / 已使用 / 已过期。但「已过期」不应该落库。

如果 `status` 需要存 `EXPIRED`，就必须有人负责修改它：某个码在周三 15:00 过期，15:01 时它的状态就应该已经是 `EXPIRED`，这需要一个定时任务不断扫表。

而 `expires_at` 已经存下来了，校验时与当前时间比较即可得出结论，不需要任何后台任务。

因此 `status` 只有两个值：`PENDING`、`USED`。

一般规律：**能由已有数据算出来的结论，不要另外存一份。** 存下来的会过时，算出来的永远正确。

### 4.5 同一用户的多个未使用邀请码不需要额外处理

小 A 连续点击三次「邀请伴侣」，表中会有三行 `PENDING`：

| id | inviter_id | code | status |
|---|---|---|---|
| 1 | 1 | 7F3K9M | PENDING |
| 2 | 1 | X2P8QR | PENDING |
| 3 | 1 | M4T7WZ | PENDING |

小 B 使用 `7F3K9M` 绑定成功后，剩余两个码不需要主动作废：任何人持 `X2P8QR` 来绑定，都会被第 5 条校验（发码人是否仍单身）拒绝。

一条校验规则同时解决了两个问题。业务规则想清楚之后，很多看似需要专门处理的情况会自行消失。

### 4.6 邀请码以明文存储

邀请码需要按值查询，明文存储最直接。

邀请码不是密码：有效期 24 小时、一次性使用、即使泄露，使用者还必须自身单身才能绑定成功。当前版本不做摘要存储。

### 4.7 邀请码字符集

使用 6 位大写字母与数字，排除容易混淆的字符 `0`、`O`、`1`、`I`、`l`。

这个码需要用户从聊天窗口手工抄写到输入框，可读性直接影响成功率。

### 4.8 索引设计

- `PRIMARY KEY (id)`；
- `UNIQUE (code)`：保证唯一，同时支持按码查询；
- `inviter_id` 单列索引：查询某用户发出的邀请时使用。

## 5. 与 Java 对象的对应关系

数据库使用下划线命名，Java 使用小驼峰。项目已在 `application.properties` 开启 `mybatis.configuration.map-underscore-to-camel-case=true`，无需为此单独编写结果映射。

| 数据库字段 | Java 属性 |
|---|---|
| `user_a_id` | `Long userAId` |
| `user_b_id` | `Long userBId` |
| `bound_at` | `LocalDateTime boundAt` |
| `inviter_id` | `Long inviterId` |
| `expires_at` | `LocalDateTime expiresAt` |
| `used_at` | `LocalDateTime usedAt` |

`status` 当前使用 `String`，暂不引入枚举与类型处理器。

## 7. 已知边界与未决事项

1. 「一个用户最多一段有效关系」没有数据库约束兜底，仅由 Service 保证，存在并发窗口。第 6 周学习并发一致性时处理；
2. 结束关系功能本周不实现。`ended_at` 字段暂不添加：它不参与任何查询条件，将来作为可空列追加不会影响现有代码；
3. 是否为 `user_a_id`、`user_b_id`、`inviter_id` 添加外键约束尚未决定。外键能让数据库拒绝指向不存在用户的记录，代价是插入测试数据时对顺序有要求。当前 `users` 表未使用任何外键，留到第 5 周设计挑战关联表时统一决定；
4. 邀请码有效期定为 24 小时。选择短有效期的一个实际原因是便于构造过期用例进行测试。
